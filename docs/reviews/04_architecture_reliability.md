# Review 4 — Architecture, Reliability & Zero Maintenance

Reviewer role: adversarial check of whether this system runs unattended for 1–3 years. Not a redesign. References: `ARCHITECTURE.md`, `DATA_MODEL.md`, `DEPLOYMENT.md`, `ADMIN_UX.md`, `ANTI_CHEATING.md`.

---

## CRITICAL

### 1. Infra downtime silently fails candidates via the hard server-side deadline
`deadline_at` is written once and never re-armed (`items_served_once` trigger, `DATA_MODEL.md` §3.11). If the single Render instance restarts — a crash, an OOM under `--max-old-space-size=384`, a failed health check, or just the ~30–90 s window a redeploy's new instance needs to boot and pass `/api/health` — any candidate whose item is "in flight" during that window has their deadline keep ticking against a server that isn't answering. When service resumes, `now() > deadline_at + 2s grace` and the item is recorded `expired` with no answer, silently docking a real pillar score for an outage that was entirely infrastructure's fault, not the candidate's. There is no compensating mechanism (no "extend session by observed downtime," no flag on the result noting an outage occurred). Nobody will notice because integrity/results review never cross-references platform incidents.
**Fix:** on `/api/health` failure or process restart detection, either (a) extend in-progress sessions' `expires_at`/item deadlines by the measured outage duration on next resume, or (b) at minimum stamp affected items/sessions with a `server_outage_suspected` flag (compare `received_at` gaps > N seconds against expected request cadence) so the admin sees "this candidate may have been failed by an outage, not by lateness" instead of a clean-looking `expired` row.

### 2. Retention promises (90-day IP nulling, digest) depend on an optional Postgres cron that may never run — data is quietly retained forever
`DATA_MODEL.md` §3.13/§8 promises full IP is "nulled after 90 days lazily" — but the *only* trigger for that nulling is an admin opening that specific candidate's record, or a `pg_cron` job the design explicitly says may not exist ("only if the Supabase plan offers it — the design does not depend on it," `ARCHITECTURE.md` §8). A rejected candidate nobody re-opens keeps a full IP address forever, contradicting the retention statement made in the consent text (`consents` table, `CANDIDATE_FLOW.md`). This is not a hypothetical: most applicants to a screening funnel are rejected and never revisited. Same mechanism (optional `pg_cron`+`pg_net`) underlies the "daily digest" email in `ADMIN_UX.md` §"Admin" — a feature that will simply never fire on any Supabase project where those extensions aren't enabled, with no error, no admin-visible indicator that it's off, and no one who will ever check.
**Fix:** Don't make a compliance-relevant retention control dependent on an optional extension. Either (a) confirm `pg_cron`/`pg_net` at setup time and fail the setup runbook loudly if unavailable, or (b) do the IP-nulling sweep as a cheap side effect of an *unconditional* frequent path — e.g. piggyback on the admin list's own query (`UPDATE ... WHERE created_at < now() - 90d AND ip IS NOT NULL LIMIT 500` fired probabilistically on any admin page load, the same pattern already used for `rate_limits` cleanup). Drop the digest's silent-optional dependency entirely or replace it with the "count on the list header" fallback as the only implementation (which the doc already describes as acceptable) rather than a two-tier feature that can silently be the weaker tier forever.

### 3. Zero real alerting: a broken template family or a scoring regression fails 100% silently
Per `ARCHITECTURE.md` §10, the entire observability story is stdout logs on Render (short retention, nobody tails them) and an *optional*, off-by-default Sentry DSN. There is no alert on 5xx rate, no alert on health-check failures beyond Render's own instance restart, no alert if a template family's accuracy craters to 0% or 100% (which the bank-analytics page in `ADMIN_UX.md` §"Bank" can only reveal if a human manually opens it and knows what a healthy baseline looks like), and no alert if the boot-time schema-mismatch path (`DEPLOYMENT.md` §9) actually fires. For a system whose entire premise is "an engineer touches this code six months or two years from now and might introduce a subtle bug," the design has no mechanism to surface that bug except a hiring manager noticing candidates' scores "look weird" — which they have no baseline to judge against, since camera/proctoring and manual review are also absent by design. This directly undermines the stated goal: a broken deploy that silently degrades scoring quality (not a crash — a wrong answer key, a mis-rendered SVG in RTL, a shuffled-options bug) can run for the entire remainder of a hiring round before anyone notices, and there's no evidence anyone would notice at all.
**Fix:** Make Sentry (or an equivalent free-tier error tracker) on by default, not opt-in — it's a config value, not a workload. Add one lightweight scheduled check that *is* zero-maintenance: a same-request, cheap invariant check baked into the admin list page load (e.g., "any template family in the last 50 served instances has accuracy outside [10%, 95%]? Show a banner.") so the exact person who is already looking at the system periodically gets a passive signal, without needing a pager.

### 4. Node 20 is already past its LTS support window as of the stated project timeline
`DEPLOYMENT.md` mandates Node 20 on Render, and `ARCHITECTURE.md` §8 explicitly says dependency updates are "not required for operation" and Renovate is deliberately not configured — i.e., the plan is to pin Node 20 and every npm dependency indefinitely. Node.js 20 ("Iron") exits LTS / stops receiving security patches in April 2026. Given the project is meant to run untouched for 1–3 years, it will spend most or all of that lifespan on an unsupported Node runtime with no patches for newly discovered vulnerabilities, and no one will be watching for that because dependency/EOL monitoring was deliberately turned off. This isn't a generic "keep dependencies fresh" platitude — it's a specific, dated fact about the exact runtime version this doc mandates.
**Fix:** At minimum, bump the target/pin to whatever Node LTS will still be supported furthest into the intended lifespan at launch (Node 22, LTS into 2027), and explicitly scope "no Renovate" to mean "no *routine* dependency bumps," not "never touch the Node major version." Consider a once-a-year calendar reminder (not a technical job — literally a note to the hiring manager: "ask someone to bump Node major version and redeploy") as the one deliberate exception to zero-maintenance, since EOL runtimes are a security exposure, not a cosmetic one.

## IMPORTANT

### 5. The "migrate then deploy" ordering is safe only for additive migrations — nothing prevents a future destructive migration from breaking the gap between the two manual steps
`DEPLOYMENT.md` §5 documents the order as `supabase db push` → merge to `main` → Render deploys, justified by "migrations are always backward-compatible... add columns nullable, never rename in one step." That rule is real and correct *if followed*, but it is pure human discipline with zero tooling enforcement: no CI check verifies a migration is additive, no staging database exists to catch a violation (`TEST_STRATEGY.md` has no staging environment — pgTAP runs against a local/test Supabase instance, not a pre-prod copy of the real one), and the old app version keeps serving live traffic against the new schema for however long the gap between `db push` and the Render deploy completing happens to be (minutes if scripted back-to-back, much longer if a human runs the migration and then goes to lunch before merging). A single accidental `DROP COLUMN` or `NOT NULL` addition in that gap takes the live site down with no code change involved — and no auto-rollback path exists for a *migration* mistake (the boot-time check only guards code-vs-schema mismatch in one direction: old-code-needs-old-schema was never a case the design tests for).
**Fix:** Document the expand/contract pattern explicitly (add in release N, stop reading in release N+1, drop in release N+2) as a hard rule with a worked example, not just a one-line aside. Consider a trivial CI check that fails on migrations containing `DROP COLUMN`/`ALTER ... NOT NULL`/`RENAME` without an explicit `-- deferred-safe` marker.

### 6. "Manual Supabase CLI migrations" quietly requires an engineer forever for exactly the scenarios the business will actually hit
The claim in `DESIGN_SUMMARY.md`/`ARCHITECTURE.md` that this is zero-maintenance is true for the common case (new job with the *same* assessment shape — confirmed: `jobs` is just a new row referencing the existing `assessment_configs` row, no schema or code change needed, `ADMIN_UX.md` "Jobs"). But the two most plausible six-months-from-now requests are **not** covered by that path: (a) a genuinely different assessment shape (different block counts/time limits/pillars) requires a new `assessment_configs.blueprint` row, and there is no admin UI to author one — the blueprint is "validated by zod... at load time" (`DATA_MODEL.md` §3.3), i.e. authored by someone who can write JSON matching a schema and can run a migration/seed script; (b) any schema fix (a missing index, a new candidate field, a bug in a trigger) requires exactly the CLI + repo + Supabase credentials + redeploy flow. Both are realistic 1–3-year events for a live hiring pipeline, and both require finding an engineer, not the hiring manager. This should be stated plainly rather than implied away by the "new jobs reuse the config" example, which is the *easy* case.
**Fix:** Nothing to change technically — but the docs should say explicitly, in one place a non-technical reader will see (`DESIGN_SUMMARY.md` or a short runbook), "no maintenance is needed unless you want a differently-shaped assessment or a schema change — those need a developer, budget for that as a known future cost," rather than let "zero maintenance" be read as "never need a developer again."

### 7. Graceful shutdown on deploy/instance-swap is unaddressed
`DEPLOYMENT.md` describes Render's health-check-gated deploy and instance restarts, but nothing in `ARCHITECTURE.md`/`DEPLOYMENT.md` mentions the Next.js server handling `SIGTERM` to drain in-flight requests before Render kills the old instance during a swap or a crash-restart. Each candidate request is short (~tens of ms per the docs' own numbers), so the exposure window is small, but a `POST /api/assessment/answer` killed mid-transaction during exactly that window could leave an item in an inconsistent state (served but with an answer partially written, or none) for one unlucky candidate per deploy. This is a small, real gap in an otherwise carefully reasoned request-flow design, and worth one sentence of explicit handling given how much care went into e.g. the `items_served_once` trigger for a similar class of race.
**Fix:** Confirm Render's default grace period for the target plan and add an explicit `process.on('SIGTERM', ...)` drain (or confirm Next.js's standalone server already does this) in the deployment doc so it's not an assumption.

### 8. DB/Storage growth has no plan-limit tripwire, and retention is explicitly "keep everything forever"
`DATA_MODEL.md` §8 states there is deliberately no purge job — full stop, "the hiring manager may want to revisit past applicants." Combined with no purge and years of hiring rounds, `integrity_events` (append-only, dozens of rows per session) and `assessment_items`/`assessment_responses` (full rendered content + answer keys retained forever, `DATA_MODEL.md` §3.11) will grow monotonically. At the volumes discussed (hundreds→thousands per round, over 1–3 years and multiple roles) this is very unlikely to blow through Supabase Pro's 8 GB included DB or 100 GB storage in absolute terms, but there is zero visibility into the trend — no health-check field, no admin-dashboard number, nothing surfaces "DB is at 60% of plan" before an overage bill or a hard limit surprises the hiring manager. This is a low-probability, high-surprise failure mode precisely because nobody is watching the one thing (project cost/size creep) a non-technical owner has no way to introspect.
**Fix:** Add a single line item to `/api/health` or the admin dashboard footer that reports Supabase project DB size (already queryable via `pg_database_size` or Supabase's own project usage API) so the hiring manager sees it every time they're already looking at the page — no new job needed, just render one more number that's already known.

## MINOR

### 9. Backup/DR is "enabled at setup," never verified
`DEPLOYMENT.md` §11 documents Supabase daily backups and an optional PITR add-on, and states "Disaster recovery = new Supabase project + restore backup + update Render env vars. Documented in README runbook (10 lines)." Nothing in `TEST_STRATEGY.md` includes actually exercising a restore before launch or on any cadence after. An untested backup is a hypothesis, not a recovery plan — the failure mode (a bad migration or bad admin bulk-action corrupts data, and the "10-line runbook" turns out to have a gap, e.g. the storage bucket objects aren't included in the described restore path) would only be discovered during a real incident, which is the worst possible time to discover it.
**Fix:** Add "restore the backup into a throwaway Supabase project and smoke-test it" as a one-time pre-launch step in `TEST_STRATEGY.md` §9 (the pilot section already exists as a natural place to bolt this on), not just an assumed capability.

### 10. Single Render instance + autoscale off means one crash-loop (e.g., from a bad `DATABASE_URL` after a Supabase key rotation) is a full outage with no automatic operator notification beyond Render's own deploy-failure email
This is an acceptable trade-off at this scale (explicitly reasoned about in `ARCHITECTURE.md` §2, and a second instance is "a one-line change" if needed) — flagging as minor only because the design should say, in the runbook, what the hiring manager should expect to see (an email from Render) and whom to forward it to, since "nothing to operate" can otherwise be read as "nothing can go wrong."

### 11. Single-region, single-cloud-vendor-pair (Render + Supabase, both Frankfurt) with no status-page subscription
Reasonable for cost/complexity at this scale, but the design doesn't mention subscribing the hiring manager (or a distribution list) to Render's and Supabase's status pages. For a "zero maintenance" target, passive awareness of provider incidents (rather than only discovering one via a candidate complaint) is a free, zero-maintenance addition.

---

## Overall verdict

The core request/response architecture is genuinely sound for zero-maintenance operation in the common case: no in-memory session state makes the single-instance, zero-downtime-deploy story hold up, the "no cron" claim is true for the vast majority of documented functionality, and the migrate-before-deploy ordering is safe *as long as* the stated backward-compatibility discipline is never violated. But "zero maintenance" is currently oversold in three concrete ways that will surface as real incidents over a 1–3 year unattended life: outages silently cost real candidates real score damage through the hard server deadline with no compensation and no alert (#1); two retention/notification features quietly depend on an optional Postgres extension that may simply never be enabled, so a written privacy promise (90-day IP deletion) can go unfulfilled indefinitely with no one the wiser (#2); and there is effectively no alerting layer, so a subtle bug shipped by whatever engineer touches this code in year two — a broken template, a scoring regression, a failed schema migration — has no mechanism to reach the hiring manager's attention short of a candidate complaining or someone happening to eyeball the bank-analytics page. None of these require a redesign to fix — they're each a small, bounded addition (an outage-aware flag, an unconditional retention sweep, a default-on error tracker) — but as written, the system will run unattended right up until the day one of these gaps matters, and on that day it will fail silently rather than loudly, which is the worst possible failure mode for a system nobody is watching.
