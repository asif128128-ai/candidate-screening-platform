# Implementation state

Read this first if you're picking up this project cold. It tells you what
exists, what's a placeholder, who owns each placeholder, and what to do
next. The design spec is in `docs/` — read `docs/DESIGN_SUMMARY.md` §7 for
the reading order if you haven't already. This file was written by the
engineer who did the **foundation-only** pass: scaffold, database schema,
deployment config, testing setup. No candidate flow, assessment engine, or
admin dashboard logic was implemented beyond typed placeholders.

For decisions made where the spec was silent or two docs disagreed, see
[`IMPLEMENTATION_NOTES.md`](IMPLEMENTATION_NOTES.md) — this file cross-links
to it rather than repeating it.

## What's built (foundation layer — done)

### Project scaffold
- Next.js 15.5.25 (App Router, TypeScript, strict mode, `noUncheckedIndexedAccess`), pnpm.
- Tailwind CSS 3 configured for RTL via logical-property utilities (no
  physical-direction classes) — enforced by a custom local ESLint rule at
  `eslint-rules/no-physical-direction.mjs` (see IMPLEMENTATION_NOTES.md for
  why it's hand-written rather than `eslint-plugin-tailwindcss`).
- `next-intl` wired for `he` (default, only locale live) with `en.json`
  present as the documented drop-in. Candidate pages live under
  `src/app/(candidate)/[locale]/...`; admin pages under `src/app/admin/...`
  (Hebrew-only, no locale segment) — two separate Next.js "root layouts"
  (see IMPLEMENTATION_NOTES.md).
- Full route skeleton exists for every route in `CANDIDATE_FLOW.md` §1 and
  `ADMIN_UX.md` (candidates list/detail, jobs list/new/edit, bank,
  settings, login, MFA enroll) and every API route
  `ARCHITECTURE.md` §5 names, **all as placeholders** with a
  `TODO(<engineer>) ...` comment citing the spec section that describes
  what belongs there. None of them touch the database except `/api/health`.
- `src/middleware.ts`: next-intl locale routing for candidate pages,
  security headers (CSP, HSTS, X-Content-Type-Options, Referrer-Policy) on
  every route. Admin auth gating is a named TODO, not implemented.
- `src/components/term.tsx`: the `<Term>`/`<bdi>` mixed-direction text
  helper from `ARCHITECTURE.md` §9.

### Database (`supabase/migrations/`)
- `0001_init.sql`: the **full schema** from `DATA_MODEL.md` as amended by
  `DECISIONS_LOG.md` — every table (§3.1–3.20), the `admin_application_rows`
  view (§4), all invariant triggers (`items_served_once`,
  `items_deadline_immutable`, `results_immutable`, §5), the `app_user` role
  with `NOBYPASSRLS` and explicit grants (§6.1), request-context RLS on
  every table (§6.2–6.3), and the storage bucket (`DEPLOYMENT.md` §6).
  - `SECURITY DEFINER` functions: `cv_upsert`, `delete_candidate`,
    `delete_application`, `apply_outage_credit`, `finalize_session`,
    `prune_retention`, `run_maintenance_sweep` — all per their spec
    sections in `DATA_MODEL.md`/`ARCHITECTURE.md`.
  - `cv_files` → `cv_purge_queue` trigger (`cv_enqueue_purge`) per §3.9.
  - `run_maintenance_sweep()` implements the hourly-lock scheduler
    (§8) and two of the six invariant checks fully; the other four are
    named `TODO`s blocked on data that doesn't exist yet — see
    IMPLEMENTATION_NOTES.md.
- `0002_seed.sql`: `assessment_configs` (`default_tech_student_v1` with the
  exact blueprint from `DATA_MODEL.md` §3.3) and the one active job
  (`student-tech-2026`), text copied from `CANDIDATE_FLOW.md` §3.1 (see
  IMPLEMENTATION_NOTES.md for why not the doc's literal citation).
  `admin_users` is deliberately **not** seeded — created via
  `pnpm admin:add` per `DEPLOYMENT.md` §8 step 3.
- `supabase/config.toml`: local dev stack config (matches ports/settings
  DEPLOYMENT.md implies: Auth with mandatory-capable TOTP, sign-ups off,
  Storage 5 MiB limit).
- `supabase/tests/database/0001_smoke.test.sql`: one trivial pgTAP test
  (table existence). Real RLS/trigger/cascade coverage
  (`TEST_STRATEGY.md` §7) is not written yet.
- **Not executed against a live Postgres** — no Supabase project exists in
  the environment this was built in. Run `supabase db push` and
  `supabase test db` against a real project before trusting it further;
  read every migration once yourself first, this is a lot of SQL written
  without a live database to catch typos.

### Deployment
- `render.yaml` matching `DEPLOYMENT.md` §4 (Frankfurt, Starter, Node 22,
  `/api/health` healthcheck, all documented env vars).
- `.env.example` — every var from `DEPLOYMENT.md` §3, each with a comment
  on purpose and where to get the value.
- `/api/health` (`src/app/api/health/route.ts`) — **fully implemented**
  except the storage HEAD check (TODO, see IMPLEMENTATION_NOTES.md):
  checks DB connectivity, runs the maintenance sweep opportunistically,
  compares the DB's applied migration version against the build's
  compiled-in version (`src/generated/schema-version.ts`, regenerated by
  `scripts/generate-schema-version.ts` on every `dev`/`build`), reports
  sweep staleness and CV purge backlog, returns 503 on any of those.
- `README.md` — setup/deployment walkthrough for a technical-but-not-a-
  developer operator, mirroring `DEPLOYMENT.md` §8 with this repo's actual
  script names.
- `.github/workflows/ci.yml` — typecheck, lint, unit tests, build, e2e
  smoke, migration expand/contract check, dependency audit (warn-only), on
  every PR. `bank:audit` runs with `continue-on-error` since it's blocked
  on the generator (see below).
- `.github/workflows/migrate.yml` — manual `workflow_dispatch` job running
  `supabase db push` with a `MIGRATION_DATABASE_URL` repo secret.
- `.github/dependabot.yml` — security-alert-only config (no auto-PRs).
  **Repo-setting note**: GitHub's "Dependabot alerts" toggle itself
  (Settings → Security) still needs to be turned on by hand — no YAML file
  can do that part.
- `scripts/`: `check-env.ts` (real, run as `prestart`), `admin-add.ts`
  (real), `set-app-password.ts` (real), `sweep-now.ts` (real),
  `check-migrations.ts` (real, the expand/contract CI gate), and
  `bank-audit.ts` (placeholder — blocked on the generator).

## Decisions made without a spec answer

See [`IMPLEMENTATION_NOTES.md`](IMPLEMENTATION_NOTES.md) for the full
reasoning on each. Short list: pnpm over npm; Next.js patched to 15.5.25;
next-intl pinned to 3.26.3 (pre-v4); a hand-written ESLint rule instead of
an `eslint-plugin-tailwindcss` fork; two Next.js root layouts; the bare `/`
route; the seed job's copy source; excluding `.doc` from the storage
bucket's allowed mime types (not just the app-level check); the
migration-version boot-check mechanism; which sweep invariant checks got a
real implementation vs. a TODO; Sentry's minimal wiring; leaving admin auth
middleware unimplemented.

## Exact next steps

The suggested build order in `DESIGN_SUMMARY.md` §8 still holds. Concretely,
from here:

1. **Get a real Supabase project running** and `supabase db push` this
   schema against it. Read `0001_init.sql` and `0002_seed.sql` yourself
   first — they were written without a live database to catch mistakes
   against. Then run `supabase test db` and add real pgTAP coverage per
   `TEST_STRATEGY.md` §7 (cross-application RLS isolation is the most
   important one to get right early).
2. **Assessment-engine engineer**: implement `src/assessment/generator.ts`,
   `scoring.ts`, `integrity.ts`, `timing.ts` and the template bank, fully
   unit-tested (100% branch per `TEST_STRATEGY.md`), *before* touching any
   UI — this is milestone 2 in `DESIGN_SUMMARY.md` §8 for a reason: the
   runner and admin results views are both consumers of these pure
   functions.
3. **Candidate-flow engineer**: build steps 1–3 (`CANDIDATE_FLOW.md` §1–4)
   on top of the existing page placeholders, wire
   `src/lib/candidate-cookie.ts` into real cookie read/write, add rate
   limiting against the existing `rate_limits` table.
4. **Assessment-engine engineer** (continued): the runner UI + the two hot
   API routes, once step 2 exists.
5. **Admin-ui engineer**: auth middleware, then list/detail/jobs/settings.
6. Once there's a real backend to test against: flip
   `playwright.config.ts`'s `webServer` command to
   `pnpm build && pnpm start`, build out the full e2e suite from
   `TEST_STRATEGY.md` §2, wire the remaining sweep invariant checks, wire
   the `/api/health` storage check, and run the k6 load scenarios
   (`TEST_STRATEGY.md` §8) before the human pilot (§9).
